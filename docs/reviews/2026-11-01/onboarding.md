# Docker and new-user onboarding review

**Review date:** 2026-11-01
**Scope:** `README.md`, `docs/REUSABLE-HASHFLEET-PLAN.md`, `docs/SERVER-SETUP.md`, `src/swift_sonar_kit/cli.py`, `src/swift_sonar_kit/server.py`, and `pyproject.toml`.

## Bottom line

The repository describes a portable host-side scanner client, not a Dockerized scanner product. No `compose.yaml`, `docker-compose*`, or `Dockerfile` is present. README correctly says the toolkit does not create containers, install plugins, or administer SonarQube. The onboarding gap is that it gives no copyable recipe for safely connecting a second project to an existing server, nor a clear first-run boundary between server container setup and host analysis.

Do not present current v0.1 as HashFleet-equivalent or deeper. The plan explicitly records unproven dashboard parity, narrower Swift-only scan scope, missing xcresult identities, multi-language/configuration preservation gaps, and non-equivalent lint evidence. Keep HashFleet's existing scanner, properties, Docker server, volumes, plugin/profile, and dashboard untouched while evaluating another project.

## Practical boundary: macOS host vs Docker

- **Reuse the existing SonarQube server where possible.** Docker is an administrator-managed server deployment concern. Preserve its existing image/version, data volumes, plugin, profiles, gates, and dashboard. Do not run `docker compose down`, replace/recreate volumes, pull `latest`, or alter plugins/profiles just to onboard a consumer.
- **Run scanner/tooling on the host.** Install/use pinned Python, Git, SwiftLint and SonarScanner on the analysis machine as documented. Run `swift-sonar` with the new consumer repo as current directory or `--root /absolute/path/to/checkout`. Xcode builds, simulator tests, and xcresult tooling need macOS/Xcode. A Linux container is not an iOS test environment. Linux SwiftPM/report conversion may be a separate tested workflow, not implied parity.
- **Use the right server URL for the execution location.** On macOS host, `http://localhost:9000` works only if the server publishes that port to host loopback; a remote server must use HTTPS. If a scanner is deliberately run inside a container, `localhost` means that container, not the Mac or Sonar container. Use the Compose service DNS name on a shared network, or a controlled host gateway, and document the exact mapping. Do not expose a server publicly to make this work.
- **Pin artifacts and verify them.** The repo's compatibility target is Community Build `26.9.0.129388`, sonar-apple `0.5.1`, SwiftLint `0.65.1`, and SonarScanner `8.3.0`; these are stated local targets, not universal compatibility guarantees or a recommendation to upgrade an existing deployment. For a new Compose example, pin the server image by immutable digest (and record the human-readable version) and pin the plugin release plus verified checksum. Pin host tool versions too. `doctor` verifies server UP, exact expected plugin version, and Swift registration, but does not verify artifact provenance/checksum or certify general compatibility.
- **Project root and paths.** Start in the selected checkout root; relative `--source`, `--lcov`, artifacts, and outputs resolve there. Alternatively pass `--root` explicitly. Select explicit, in-root, non-overlapping production directories (e.g. `Sources` or the app's actual source directory), not the whole repository. Keep reports under that checkout; ignore `.swift-sonar/` and `.scannerwork/`. A containerized analysis client must mount the selected project at a documented stable path, use that same path for `--root`, ensure generated reports are inside the mount, and use a persistent writable workspace only if needed. Do not mount Docker socket or server data into the client.

### Safe existing-server reuse sequence

1. Obtain owner approval for the existing server URL, project key, profile/gate, and scoped token. Do not alter server state or grant admin permissions to satisfy preflight.
2. Confirm the URL is final and trusted. `server.validate_url` rejects credentials/query/fragment, remote plaintext HTTP, and unsafe context paths; redirects are refused. Keep `SONAR_TOKEN` in the shell/CI secret store, never in repo config or argv.
3. Run `swift-sonar doctor` with the selected expected plugin version. A mismatch stops; the command does not upgrade anything. Confirm read permission for plugin inventory without broadening privileges automatically.
4. In the new repo, run tests/artifact generation, then `swift-sonar scan ... --prepare-only`; inspect the generated summary, scope, and reports. Only explicit `scan` publishes source/analysis. Use a distinct project key for parity comparison and a dedicated profile if generic SwiftLint issues are enabled. Do not switch an existing shared profile or conflate generic external issues with the plugin's native SwiftLint sensor.

## Top three onboarding gaps and acceptance tests

1. **No safe, copyable existing-server + second-project recipe.** README has a SwiftPM quick start and mentions Xcode, but no end-to-end macOS recipe showing a second checkout, URL semantics, separate key/token, `doctor`, preparation review, and explicit publish. The server guide begins with a disposable/staging instance and does not explain reuse of an already-administered server.
   **Acceptance:** In an integration test with a fake Sonar API, a user selects a path containing spaces, sets a distinct project key and secret token, runs `doctor`, and prepares successfully; test asserts token is absent from argv/output/files, invalid remote HTTP and redirects fail closed, wrong plugin version stops without any mutation, `--prepare-only` makes no network/scanner call, and only explicit publish invokes scanner. Manual staging acceptance verifies an existing project/dashboard/profile remains unchanged.

2. **No Docker networking, pinning, persistence, and non-destructive setup example.** The docs state policy but offer neither an example configuration nor a clear guard against destructive reset/replacement; new users may infer they need a new server or may accidentally target `localhost` from the wrong network namespace.
   **Acceptance:** A reviewed sample Compose config pins image digest and plugin checksum/release, persists all required server data, publishes only intended host interface/port, and has no automatic plugin download/restart or destructive reset instructions. In an isolated disposable server test, host `doctor` reaches it via the documented URL; if a client container recipe is included, it reaches the service via service DNS and its mounted project root. A regression check confirms onboarding commands never invoke Compose or alter volume/profile/plugin state.

3. **No generic per-project config contract to preserve HashFleet-depth scope.** Current `scan` only accepts explicit Swift source roots and LCOV, freshly lints selected roots, generates a focused properties file, and does not merge/reuse existing multi-language Sonar properties. Plan calls the shared schema/config and xcresult support future design. The existing test receipt proves only the selected command exit and artifacts, not exhaustive test census.
   **Acceptance:** For a representative non-HashFleet Swift app, freeze revision/tool versions and use isolated Sonar keys/profiles; compare classified Swift plus tooling file inventory, nonempty lint issue tuples, coverage executable-line observations/denominator, and independent test identities against its established pipeline. Include failing tests/lint, stale/mutated artifacts, paths with spaces, multiple roots, excluded generated/vendor/test files, and preserved Python/multi-language properties. No “same or deeper” claim until accepted baseline evidence is retained and any added checks are separately labeled.
