# Server setup and adoption

## Select the server path

The default `./scan PATH` runs strict SwiftLint and Sonar source analysis only. It does not build applications, run tests or simulators, archive builds, or collect/import coverage and native results. Valid lint findings still reach Sonar and keep the overall exit nonzero. Execution errors and invalid findings stop before publication. See [the default workflow](PATH-ONLY.md).

- **Existing server:** select it with `--url URL` or `SONAR_HOST_URL`; provide `SONAR_TOKEN` through a secret store. This suppresses local Docker provisioning. Remote servers must use HTTPS. Scanning publishes source and analysis to that server.
- **Automatic local server:** the no-URL full `run PATH` invocation opts in to a kit-owned SonarQube Community Build instance. It needs a local Docker daemon. If the pinned image is missing, the kit attempts a bounded 180-second pull by immutable digest, then verifies the exact repository digest and expected Sonar version. It downloads the sonar-apple plugin if absent and verifies its expected size and SHA-256 before mounting it read-only.

Historical receipt, not acceptance of the current source-only default: the frozen version 0.3.0 `OrbitMath` SwiftPM acceptance run completed a real test-driven scan: strict lint, tests, production-only LLVM coverage with covered and uncovered source lines, artifact binding, isolated local-server setup, analysis submission, and scanner-reported `QUALITYGATEPASSED` (exit 0). It ran from paths containing spaces. A repeat run exited 0 and reused the exact same container ID. Read-only server API checks confirmed quality gate OK, 85.7% coverage, 7 lines to cover, and 1 uncovered line, matching XML line 5 covered and line 7 uncovered. Metadata identified a project-scoped token for `OrbitMath`; checks confirmed default admin-password rejection, loopback-only binding, and private 0700/0600 storage. The frozen wheel runtime matched the checkout. An earlier Docker Desktop bind-path attempt failed safely before server start/upload; a narrow correction was applied and the failure receipt retained. The portable regression suite ran 237 tests (235 passed, 2 external native-fixture checks skipped). The installed wheel outside the checkout without `PYTHONPATH` passed local preparation and repeat/archive checks. See the [dated acceptance report](PATH-ONLY-ACCEPTANCE-2026-11-07.md). These receipts establish only the tested SwiftPM fixture and same-container repeat, not universal Xcode support, restart recovery, or sustained uptime. The scratch fixture service is not a permanent server. Optional XcodeWarnings, Periphery, and MobSF sensors logged command/parsing errors without inputs, so those analyzers were not successfully run and are outside the acceptance scope. The separate actual consumer `./scan PATH --prepare-only` remains blocked at preflight by 29 lint findings; tests were not run and publication was false.

## Automatic instance boundaries

The implementation pins Community Build image `sonarqube@sha256:aa7146fd72ef79ea8ca06315ca3121db9bb1c24a83ba5255e8df67b43dee6e04`. If it is not already available locally, Docker image pull is attempted with a 180-second timeout; the resulting image must report the exact pinned `RepoDigests` identity and expected `SONAR_VERSION=26.9.0.129388`. The implementation pins sonar-apple plugin `0.5.1`. Its artifact is fetched from the upstream GitHub release over HTTPS and checked against SHA-256 `c27432e52a6ebc698b77ad42bf3d98f5e34fb20d3f398799bda74fbc008f8612` and the expected byte length. The plugin performs Swift registration. This is a local compatibility configuration, not proof of broad parser or project support.

For each canonical project root and project key, the container identity is `swift-sonar-<normalized-key-slug>-<20 hex chars>`, where the suffix is derived from SHA-256 of the root, a NUL separator, and the exact project key. Docker ownership labels bind resources to that identity/root/key and a private nonce. The server port is dynamically allocated but published only on `127.0.0.1`; Docker must use a local Unix socket, not a remote daemon. It creates four project-named local volumes (`data`, `extensions`, `logs`, `temp`) and a read-only plugin-file mount.

Private state and generated credentials are stored outside the project under `~/.local/share/swift-sonar-kit/servers/<container-identity>` with user-only directory permissions (`0700`) and private state/lock files (`0600`). The plugin cache is under `~/.cache/swift-sonar-kit`, also private. The state includes generated administrator and project-analysis credentials, so protect and back up this private state as sensitive data; do not copy it into the project, logs, shell arguments, or source control. The analysis token is project-scoped.

Provisioning validates exact ownership labels, image, mounts, port mapping, and state before starting/reusing a matching instance. An unowned name collision or missing/mismatched resource fails closed without modifying it. Setup retains private state for recovery on errors, does not reset or delete resources, and does not rename, restart, or take over another container. The legacy container name `hashfleet-sonar` is not the new default and is never modified by this flow. The kit does not change quality profiles. Existing focused commands (`doctor`, `scan`, `project-scan`, `project-run`) keep their configured-server behavior and do not provision Docker servers.

## Existing-server adoption

1. Choose a disposable/staging Community Build instance and pin a compatible sonar-apple release. Consult [validation](VALIDATION.md) for combinations actually exercised, not a promise that every newer version works.
2. Review plugin origin, license, and artifact checksum. Installing a plugin or restarting an existing server is an administrator-controlled change, not performed by these focused commands.
3. Install host tools separately: Python 3.11+, Git, Swift/SwiftPM or Xcode as required by the project, SwiftLint, and SonarScanner. Docker can host SonarQube but cannot replace the macOS Apple toolchain required for Xcode builds/tests.
4. Create a dedicated analysis project and appropriately scoped token. Preflight reads installed plugins, so confirm that permissions permit this; do not grant administrator access merely to bypass a failed check.
5. Set `SONAR_HOST_URL` and `SONAR_TOKEN` through shell/CI secret management, or pass `--url` and keep the token in `SONAR_TOKEN`. Never put the token in command arguments, committed properties, or consumer project files.
6. Run `swift-sonar doctor` against the intended server. It checks health, plugin version, and Swift registration. A mismatch is a stop, not an automatic upgrade.
7. Run `./scan "/path/to/My Project" --prepare-only`, inspect the plan and reports, then explicitly select the existing server for any publishing run.
8. Review project-specific quality profile and gate settings. The default source-only runner imports its fresh local SwiftLint findings as generic external issues and restricts optional native plugin executable lookup to avoid duplicate lint execution. It does not modify profiles. Other focused/advanced commands retain their own import policies, so review native versus generic SwiftLint duplication when selecting those workflows.

Portable unit tests should not require installed SwiftLint, SonarScanner, Docker, or a real Xcode installation. The frozen suite result was 237 tests (235 passed, 2 external native-fixture checks skipped); those fixture checks are not folded into the real OrbitMath scan receipt. The real run establishes only its specific SwiftPM path/configuration, not universal Xcode or analyzer compatibility. A clean sample gate does not certify parsing of all Swift language features or provide SonarSource's commercial analyzer. Keep native tests, independent coverage verification, and any existing security checks.
